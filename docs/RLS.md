# Row-Level Security Policy Reference

This file documents the RLS policies on every public table. The generated schema docs in [`dbdoc/`](../dbdoc/README.md) cover structure (columns, constraints, indexes, FKs) but tbls does not introspect policies, so this file fills that gap by hand.

**Maintenance contract:** policies change only through files in `supabase/migrations/`. Any migration that creates, alters, or drops a policy must update this file in the same PR. The schema-docs CI workflow fails a PR that touches policy SQL without touching this file.

## Concepts

- **`my_team_role(team_id)`**: returns the calling user's role on the given team, resolved from `team_members` via `auth.uid()`. The role column allows exactly `raider`, `officer`, or `team_leader` (top tier within one team; named by [#294](https://github.com/katogaming88/WGA-Raid-Hub/issues/294) to stay distinct from site admins). Officer-gated policies accept `officer` or `team_leader`; team-leader-gated policies accept `team_leader` only. No policy grants a `raider` role any team data, though a member of any role can read their own `team_members` row through the self-read policy ([#212](https://github.com/katogaming88/WGA-Raid-Hub/issues/212), see the matrix note); being on a team's roster otherwise grants no access beyond public read.
- **`is_site_admin()`**: true when `auth.uid()` appears in `site_admins`. This is a separate, global mechanism, not a `team_members` role: site admins pass every policy that ORs it in ("+site" in the matrix) on every team.
- **`is_guild_officer()`**: true when `auth.uid()` appears in `guild_officers` ([#607](https://github.com/katogaming88/WGA-Raid-Hub/issues/607)). Structurally identical to `is_site_admin()` -- a standalone table, granted/revoked manually by a site admin (`admin.html`'s Guild Officers tab), not a `team_members` role or derived from holding `officer`/`team_leader` on some other team. Narrower than site admin: OR'd into only `players`/`attendance` write, `audit_log`/`team_members` read, and the `write_audit_log()`/`set_guild_officer_bios()` function gates ("+guild" in the matrix). Deliberately never OR'd into approvals, season settings, priority generation, or loot import -- a guild officer is denied there exactly like a raider.
- **Public read**: `FOR SELECT USING (true)`. The site's public pages (roster, loot feed, standings) read these tables anonymously.
- **`claude_readers`**: nologin group role for read-only AI/analysis access. Holds one `Claude readers read <table>` SELECT policy on every public table, scoped `TO claude_readers` only. Created by `supabase/roles.sql`; see [claude-readonly-db-access.md](claude-readonly-db-access.md). Add a matching policy when adding a table.
- **Service role**: Supabase's `service_role` bypasses RLS entirely. Tables listed below with no write policy are writable only through the service role (or direct SQL as `postgres`).

## Per-table policy matrix

### How to read this matrix

RLS is deny-by-default: with RLS enabled (it is, on all 36 tables), nobody can touch any row unless a policy explicitly grants it. Policies are additive; if any one policy matches an actor and operation, the action is allowed. Each row below summarizes which grants exist for that table.

- **Public SELECT**: "yes" means a `FOR SELECT USING (true)` policy exists, so anyone (including anonymous visitors) can read every row. This is how the public site serves roster, loot, and standings without login. "no" means there is no public read path.
- **Officer**: what a team officer can do, scoped to their own team's rows via `my_team_role(team_id)`. "all ops" covers SELECT, INSERT, UPDATE, and DELETE. "SELECT, UPDATE" means they can see and modify existing rows but cannot insert or delete. Team leaders pass every officer check too, since these policies accept both roles.
- **Team leader**: grants beyond the officer policies. "(via officer)" means no separate team-leader policy exists; team leaders qualify under the Officer column. "all ops +site" marks team-leader-only write policies that officers do NOT pass. "+site" anywhere means site admins are OR'd in via `is_site_admin()` regardless of team.
- **Notes**: exceptions and known gaps.
- **A blank cell** means no policy grants that actor anything, so deny-by-default applies. A table with only Public SELECT (like `classes_specs` or `teams`) is a read-only lookup: everyone can read it and only the service role can write it. A table blank in every column except Notes (`site_admins`) is invisible to everyone but the actor named there.

One thing the matrix hides on purpose: every table also carries a `claude_readers` SELECT policy (uniform across all 36 tables, so it is stated here instead of as a column).

## Views and functions

None of these carries a policy of its own. The view and the `SECURITY INVOKER` function defer to the table policies above; the `SECURITY DEFINER` function deliberately bypasses them for one specific, validated operation.

- **`pending_roster`** (view): the officer worklist of approved signups awaiting a roster add (`season_signups` where `status = 'approved'` and `approved_player_id is null`, joined to `classes_specs`). Created `WITH (security_invoker = on)`, so it runs with the caller's privileges and the `season_signups` policies apply to whoever queries it: anon and raiders see zero rows, officers and team leaders see their own team. SELECT is granted to `anon` and `authenticated`; the grant is safe because the underlying policies do the filtering.
- **`incoming_roster`** (view): a raider-facing preview of approved signups awaiting a roster add for the team's currently open signup season (#499), joined to `classes_specs` for class/spec/role and to `team_settings` to scope by `config->>'activeSignupSeason'`. Deliberately NOT created `WITH (security_invoker = on)` -- unlike `pending_roster`, this view is meant to surface these rows to anon and raiders, so it runs under the view owner's own reach into `season_signups` rather than deferring to that table's officer-only read rule; the column list is the actual safety boundary (display name, class, spec, role, team_id only -- no applicant note, officer note, reviewer, or timestamp column ever appears). SELECT is granted to `anon` and `authenticated`.
- **`add_signup_to_roster(signup_id, is_trial, archive_player_id, is_backup_tank, is_backup_healer)`** (function): atomically promotes an approved signup to the roster (creates or unarchives the `players` row, optionally archives a main-swap predecessor on the same team, sets `status = 'added'` and `approved_player_id`). `is_backup_tank`/`is_backup_healer` are decided at promotion time the same way `is_trial` is -- there's no column for either on `season_signups` itself. `SECURITY INVOKER`, so authorization comes entirely from the caller passing the existing `players` write and `season_signups` update policies. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public` (re-granted explicitly since adding these two trailing parameters produced a distinct function rather than replacing the original in place, and a brand new function doesn't inherit the original's grants).
- **`claim_character(team_id, name_realm)`** (function): links a raider's chosen character to their person row, setting `players.team_member_id` and creating the `team_members` row (`role = 'raider'`) on a first claim, or reusing an unlinked row imported from the Discord Claims sheet ([#338](https://github.com/katogaming88/WGA-Raid-Hub/issues/338)). `SECURITY DEFINER` because a claiming raider has no role yet and cannot pass the `players` or `team_members` write policies; it validates that the character is an unarchived, unclaimed roster member of the team and derives the caller's Discord id from `auth.users` rather than trusting a parameter. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`submit_self_received(team_id, name_realm, item_name, track, source, note, slot)`** (function): a raider's self-received loot submission, inserting `pending` unless the caller is authenticated as the named character (`players.team_member_id -> team_members.auth_user_id = auth.uid()`) and the source is not `Other`, in which case it inserts `approved` immediately and writes the `Self-Received Auto-Approved` audit entry itself ([#406](https://github.com/katogaming88/WGA-Raid-Hub/issues/406); auto-approve narrowed and audited by the two `20260819*` migrations). `slot` carries the raw `bis_items.slot` the approval sync targets (#386). Rejects outright (no insert at all) when `note` mentions "raid" as its own word -- actual raid drops are recorded by the officer's RCLootCouncil import instead, and raiders kept working around the lack of a "Raid Drop" source by describing one under `Other` (`20260828125630`). `SECURITY DEFINER` because `self_received_requests` has no INSERT policy for anyone. EXECUTE is granted to `anon` and `authenticated`.
- **`direct_mark_received(team_id, name_realm, item_name, track, source, note, slot)`** (function): an officer marking an item received on a raider's behalf, bypassing the approval queue -- inserts `approved` directly ([#406](https://github.com/katogaming88/WGA-Raid-Hub/issues/406)). `SECURITY DEFINER`, checking `my_team_role()`/`is_site_admin()` in the function body since (like `submit_self_received`) there's no INSERT policy to lean on. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`delete_self_received_request(id)`** (function): an officer deleting a single request row of any status, the correction path for duplicates and mistaken decisions ([#756](https://github.com/katogaming88/WGA-Raid-Hub/issues/756)). Locks the row, raises on not-found, and derives authorization from the row's own team (`my_team_role()` in officer/team_leader wrapped in coalesce, or `is_site_admin()`; guild officers deliberately excluded). Writes the `Self-Received Deleted` audit entry inside the function, targeting `players` with a summary-string detail, since the request row is gone afterwards. Deliberately does not touch `bis_items.obtained` (the one-way sync decision). `SECURITY DEFINER` because the table has no DELETE policy for anyone. EXECUTE is granted to `authenticated` only and revoked from `public`.
- **`is_boe_manager()`** (function): true when `auth.uid()` appears in `boe_managers`, same shape as `is_site_admin()` and `is_guild_officer()`. Guild-wide with no team parameter ([#766](https://github.com/katogaming88/WGA-Raid-Hub/issues/766), reshaping the per-team version #745 shipped): BoEs are guild property, so a grantee is authorized on every team's finds regardless of which team they raid on, and the grant persists until a site admin revokes it rather than self-revoking on demotion. `SECURITY DEFINER`; EXECUTE is granted to `anon` and `authenticated` (policies referencing it are evaluated for anon, which would otherwise error rather than resolve false, same as `is_guild_officer()`).
- **`is_any_team_officer()`** (function): true when the caller holds `officer` or `team_leader` on any team ([#766](https://github.com/katogaming88/WGA-Raid-Hub/issues/766)). Exists only to gate the `boe_managers` read, which has no `team_id` to scope by since the grant went guild-wide. `SECURITY DEFINER` for the usual reason a policy helper is: a policy reading `team_members` inline would be evaluated under the caller's own row security on that table, making its correctness depend on an unrelated policy. EXECUTE is granted to `anon` and `authenticated`.
- **`admin_grant_boe_manager(discord_id)` / `admin_list_boe_managers()` / `admin_revoke_boe_manager(discord_id)`** (functions, [#766](https://github.com/katogaming88/WGA-Raid-Hub/issues/766)): the only write path onto `boe_managers`, mirroring the guild-officer and site-admin trios exactly. All three `SECURITY DEFINER` and gated on `is_site_admin()`: handing someone the guild bank is an admin action, not something managers do to each other. Grant resolves `auth_user_id` from `auth.users.raw_user_meta_data ->> 'provider_id'` and refuses a duplicate; revoke raises when the account holds no grant; both audit-log. A null `auth_user_id` in the list means the grant has not activated because that Discord account has never signed in; `link_auth_user_to_member()` fills it on their first login. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`submit_boe_found(team_id, name_realm, item_name, track, note)`** (function): the raider-facing found-BoE submission ([#745](https://github.com/katogaming88/WGA-Raid-Hub/issues/745)), anon-callable for parity with the Google Form it replaces. `SECURITY DEFINER` because `boe_items` has no INSERT policy for anyone. Resolution is non-fatal, unlike `submit_self_received`: an unrostered finder keeps the raw `finder_name` with `player_id` null, and a BoE missing from the loot catalog keeps `item_id` null, since a found BoE is a fact, not a request. EXECUTE is granted to `anon` and `authenticated`.
- **`boe_record_listing(id, price, listed_at, note)` / `boe_record_sale(id, sale_price, sold_at)` / `boe_mark_paid(id, paid_at)` / `boe_retire(id, note)` / `boe_revert(id)`** (functions, [#745](https://github.com/katogaming88/WGA-Raid-Hub/issues/745)): the BoE lifecycle. Each locks the `boe_items` row (`select ... for update`), gates on `is_boe_manager() or is_site_admin()` in the function body (a `boe_managers` grant, never plain officer role; guild-wide since [#766](https://github.com/katogaming88/WGA-Raid-Hub/issues/766)), then validates the from-status and raises on an illegal edge. `boe_record_sale` computes the split (finder gets 20%-of-gross or the floor, whichever is larger, capped at the sale; the guild keeps the rest and absorbs the AH cut) from the `site_settings` floor/pivot constants, snapshotting both onto the row. `boe_revert` walks the correction edges (paid to sold, sold to listed-or-found nulling the money, retired to found). All `SECURITY DEFINER`; EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`set_boe_payout_settings(floor, pivot)`** (function): the only write path onto the guild-wide `site_settings.boe_payout_floor`/`boe_payout_pivot` payout constants ([#745](https://github.com/katogaming88/WGA-Raid-Hub/issues/745)). `SECURITY DEFINER`, gated on `is_site_admin()` only (money policy, narrower than the bios setter's site-or-guild-officer gate), validates the bounds, and audit-logs the change. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`get_own_signup(team_id)`** (function): a raider's own most recent season signup for the team's currently active signup season, joined to `classes_specs` for both the main and swap class/spec. `SECURITY DEFINER` because `season_signups` has no read rule for a raider at all; returns a fixed column list that deliberately omits `signup_officer_note` and `reviewed_by` so no future frontend query can accidentally request them ([#500](https://github.com/katogaming88/WGA-Raid-Hub/issues/500), same officer-eyes-only rule as #499). Returns no rows for a signed-out caller or one with no matching row. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`update_own_signup(signup_id, name_realm, class, spec, off_specs, main_swap, player_note, swap_from_name_realm)`** (function): lets a raider correct their own signup (typo, realm transfer, mislabeled main swap) while it is still `pending`, while `approved` and not yet promoted, or while already `added` to the roster **if** the row's `season` is still the team's active signup season (`get_own_signup()` only ever returns an `added` row in that state to begin with, so reaching the edit form already implies signups are open) -- in all three cases the edit reverts `status` to `pending`, clears `reviewed_at`/`reviewed_by`/`signup_officer_note`, and (for the `added` case) nulls `approved_player_id` to satisfy `season_signups_player_only_when_added`. It deliberately does **not** touch the `players` row it once promoted -- an edited signup goes back through officer review and a fresh `add_signup_to_roster()` promotion rather than writing the live roster unreviewed. An `added` signup whose season has moved on, or a `rejected` signup, cannot be edited through this function. `SECURITY DEFINER`; the ownership check rides on the `UPDATE`'s own `WHERE auth_user_id = auth.uid()` clause (same TOCTOU-safe shape as `claim_character()`) rather than a separate prior read. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`notify_player(player_id, message)`** (function): writes an in-app notification row for a raider, called from the officer-side approve/reject handlers for BiS link requests, self-received items, and M+ exclusion requests ([#151](https://github.com/katogaming88/WGA-Raid-Hub/issues/151)). Deliberately not wired to season signup approve/reject: an applicant has no `players` row (and so no way to resolve a notification target) until their signup is promoted to the roster, well after that step. `SECURITY DEFINER`, resolving `team_id` from `player_id` and checking `my_team_role()`/`is_site_admin()` in the function body -- same shape as `write_audit_log()`, and deliberately the only insert path onto `notifications` so a notification can't be forged or misattributed. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`write_audit_log(team_id, action, target_type, target_id, detail)`** (function): the only INSERT path onto `audit_log` ([#214](https://github.com/katogaming88/WGA-Raid-Hub/issues/214)); every officer write feature calls it after the fact to self-log. `SECURITY DEFINER`, gated on `my_team_role(team_id)` officer/team_leader, `is_site_admin()`, `is_guild_officer()` ([#607](https://github.com/katogaming88/WGA-Raid-Hub/issues/607) -- added so a guild officer's player/attendance/bio writes, which now pass the underlying table policy, don't then fail at the audit-log step), or `is_boe_manager()` ([#766](https://github.com/katogaming88/WGA-Raid-Hub/issues/766) -- same reason once the BoE grant stopped requiring an officer role; `js/common.js` only `console.warn`s on failure here, so without it a manager with no officer role would move money and log nothing). Both ORs widen the function beyond the writes that motivated them: either grant can now log any action on any team. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.
- **`set_guild_officer_bios(bios)`** (function): the only write path onto `site_settings.guild_officer_bios`, the guild-wide officer bio cards ([#577](https://github.com/katogaming88/WGA-Raid-Hub/issues/577), moved to `site_settings` in [the 2026-07-26 decision](database-decisions.md)). `SECURITY DEFINER`, gated on `is_site_admin() or is_guild_officer()` ([#607](https://github.com/katogaming88/WGA-Raid-Hub/issues/607) -- a deliberate reversal of that decision's site-admin-only reasoning, since a guild officer represents the same kind of cross-team authority a site admin does). EXECUTE is granted to `authenticated` only.
- **`set_team_officer_bios(team_id, bios)`** (function): the write path onto the per-team `team_settings.config -> 'teamOfficerBios'` bio cards, alongside (not replacing) the generic `set_team_setting()` for that one key. `team_settings`' own write policy (`all ops +site` in the matrix above) is team-leader-only, but this bio editor was always meant to be officer-facing -- the Officer Bios tab never gated the Save button to team leaders, so a plain officer hit "Not authorized" through the generic path. `SECURITY DEFINER`, gated on `my_team_role(team_id)` officer/team_leader, `is_site_admin()`, or `is_guild_officer()` -- same admission set as the `players`/`attendance` officer-write policies. EXECUTE is granted to `authenticated` only.
- **`admin_list_guild_officers()` / `admin_grant_guild_officer(discord_id)` / `admin_revoke_guild_officer(discord_id)`** (functions, [#607](https://github.com/katogaming88/WGA-Raid-Hub/issues/607)): grant/revoke/list for the `guild_officers` table, mirroring `admin_{list,grant,revoke}_site_admin()` exactly (same Discord-ID resolution, same shape). All three are gated on `is_site_admin()` only -- granting this tier is itself an admin action, not something a guild officer can do to themselves or each other. `SECURITY DEFINER`. EXECUTE is granted to `authenticated` only and revoked from `anon` and `public`.

## Known issues

- `service_role` is missing base DML grants on every table, the same defect [#284](https://github.com/katogaming88/WGA-Raid-Hub/issues/284) fixed for `anon` and `authenticated`. service_role bypasses policies but not grants, so server-side writes (Edge Functions, service-key integrations) will fail until it gets the same treatment. Flagged on #284.

## Verifying against a live database

The raw, ungrouped policy list (one row per policy, straight from `pg_policies`) is committed as [rls_policies.csv](rls_policies.csv), which opens in any spreadsheet tool for sorting and filtering. Regenerate it with `npm run db:rls` (stack running); CI fails a PR when the committed CSV no longer matches what the migrations produce. For interactive browsing, local Supabase Studio (http://127.0.0.1:54323) has a Policies page showing each table's policies with their SQL.

The same list, ad hoc in psql:

```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname = 'public'
order by tablename, policyname;
```

The vitest RLS policy-matrix harness in [`tests/rls/`](../tests/rls/) exercises these policies with impersonated anon, raider, officer, team leader, and site admin sessions and is the executable form of this document. Run it with `supabase db reset` then `npm run test:rls`.
